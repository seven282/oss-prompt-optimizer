# 兼容性策略

> 目标：**兼容未来的 dsh 版本升级，确保本插件永不成为宿主启动失败的起因。**
> 适用版本：`oss-prompt-optimizer` ≥ 1.8.4
> 相关：`scripts/preflight.mjs`、`scripts/startup-probe.mjs`、`scripts/client-probe.mjs`、
> `tests/policy-static-imports.test.ts`、`tests/client-inject-contract.test.ts`、`tests/client-apply.test.ts`

---

## 1. 为什么需要一份策略

dsh 的域包（`@deepseek-ai/dsh-llm`、`dsh-tools`、`dsh-timeout`…）仍处于 `0.1.x-rc` 阶段，
**导出会被搬迁、改名、移除**。而插件与宿主是同一个 Node 进程：

> 插件里任何一处**静态 `import` 解析失败** → 模块实例化抛错 → **不可捕获**
> → 整个 `dsh web` 起不来。代价不是"某个功能没了"，而是"整套服务无法启动"。

这不是假设。**1.8.1 的 `deepFreeze` 事故**就是这样发生的：

| 环节 | 事实 |
|---|---|
| 触发 | `@deepseek-ai/dsh-llm` 不再 re-export `deepFreeze`（该 helper 迁往 `dsh-util-values`） |
| 代码 | `lib/optimizer.js` 顶层 `import { deepFreeze } from '@deepseek-ai/dsh-llm'` |
| 后果 | 模块加载即抛错，且 ESM 静态导入的失败**无法被 try/catch 拦截** → `dsh web` 完全无法启动 |
| 教训 | 1.8.1 之前，代码里有 **7 处**同类静态宿主 import；只要其中任意一个符号变化，事故就会重演 |

因此策略的第一原则不是"兼容某个版本"，而是 **"让插件的失败面从「宿主」缩小到「一个功能」"**。

---

## 2. 三条不变量（判据）

任何兼容性改动都必须同时满足这三条，缺一条就不算解决：

| 编号 | 不变量 | 含义 |
|---|---|---|
| **I1** | **宿主启动无关性** | 本插件任何内部缺陷（依赖改名、导出消失、类型变化）都**不得**阻止 `dsh web` 启动 |
| **I2** | **单点降级** | 任一宿主契约变化最多让**一个功能**消失，不得让插件整体失效 |
| **I3** | **可验证性** | I1/I2 由脚本 + 测试**自动断言**，不依赖人记住规则 |

> **I2 在客户端半边意味着什么**（1.8.3 补充）：`exports.inject` 是**硬门禁** ——
> 列进去的服务只要有一个缺失，整个客户端半边就完全不注册（不是"少个功能"，而是"全没了"）。
> 所以客户端要满足 I2，`inject` 里只能放**真正不可或缺**的服务，其余一律走 `ctx.get()`。
> 这条以前只写在注释里，现在是规则 **R2** + `preflight` **P7**。
>
> **同一个道理还有第二种形态**（1.8.4 补充）：读一个服务的**属性**也可能被改写成读
> 一个**服务名**，从而再次撞上硬门禁 —— 见规则 **R2b**。1.8.2 与 1.8.3 两次真机全废，
> 分别是这两条规则的由来。

## 3. 规则 R1：依赖分层（核心机制）

> **R1**：`src/**` 只允许静态 `import` 两类包 ——
> **(a)** 本包 `dependencies` 里声明、**由自己安装**的包（解析自保证）；
> **(b)** 框架层 `@deepseek-ai/cordis`。
> 其余一切宿主包（`dsh-llm` / `dsh-tools` / `dsh-timeout` / `dsh-commands` / `dsh-util-values` / `dsh-system-prompt` …）
> **禁止静态 import**，只允许经 `src/compat/loader.ts` 懒加载。

**理由**：静态 import 的失败**不可捕获**，会把宿主一起拖下水；懒加载的失败**可以捕获并降级**。

### 当前允许的静态裸包 import

| 包 | 为什么允许 |
|---|---|
| `@deepseek-ai/cordis` | 宿主框架本体（`Service` 基类、`Context` 类型），与 dsh 分属不同发布线，4.x 稳定版 |
| `@deepseek-ai/schemastery` | 写在 `dependencies`，由本包自己安装，解析自我保证 |

### 类型导入的唯一正确写法

必须用**顶层** `import type`：

```ts
import type { createUserMessage } from '@deepseek-ai/dsh-llm'   // ✅ 完全擦除
import { type createUserMessage } from '@deepseek-ai/dsh-llm'   // ❌ 编译成 `import {} from '…'`
```

`verbatimModuleSyntax` 下，内联 `type` 修饰符不会被擦成空语句，而是保留一个
**空具名绑定导入** —— 它**依然是运行时导入**，依然会在模块实例化阶段去解析宿主包。
这行代码在源码里看起来"是类型、没有风险"，实际会把 1.8.1 的失败模式原样搬回来。

> 这是本项目踩过的坑：改造过程中 `src/compat/capability.ts` 一度写成内联形式，
> 产物里出现了 `import {} from '@deepseek-ai/dsh-llm'`。由 `preflight` P1 拦下。
> 现由 `tests/policy-static-imports.test.ts` 在源码层守着。

## 4. 规则 R2：客户端注入契约

> **R2**：`client/client.js` 里**只能直读已注入的服务** —— `ctx.<name>` 合法当且仅当
> `<name>` 出现在 `exports.inject` 列表里。**可选服务一律用 `ctx.get('<name>')` 读取**，
> 并自行判空；需要它的功能可以缺席，但注册流程不得中断。

**机制**：cordis 的 context 是 Proxy，`ctx.<name>` 走 `get` 陷阱 ——
名字不在 fiber 的 inject 集合里时，它**直接抛错**
（`cannot get property "<name>" without inject`）。`apply()` 并不捕获它，
于是**一处直读一个未注入的服务 = 整个客户端半边注册失败**：

```
Error: failed to apply loader entry fa1f2970 (oss-prompt-optimizer):
       cannot get property "locale" without inject
at Object.apply [as callback] (client.js:226:1)
```

`ctx.get(name)` 是另一条路径（`ReflectService.get`，源码注释原文
*"Read a service from the store without the inject requirement"*），
返回服务或 `undefined`，**永不抛错**。两者不是"写法偏好"，而是**抛错与不抛错**的区别：

| 写法 | 未注入时 | 服务缺失时的后果 |
|---|---|---|
| `ctx.locale` | **抛错** | 🔴 整个 `apply()` 失败 —— ✨ 按钮与设置页都没了 |
| `ctx.get('locale')` | 返回 `undefined` | ✅ 只少一块文案，其余功能照常 |
| `ctx.effect` / `ctx.get` / `ctx.inject` | 正常解析 | 框架内核成员，无需 inject（但仍受 R2 扫描，集合实测得出） |

### 1.8.2 的真机事故（R2 的由来）

1.8.2 把 `inject` 从 `['remote','remote.commands','settingsScope','locale','sessions']` 收敛为
`['remote']`，并把可选服务改成防御式读取 —— 但**第 226 行漏改**，`ctx.locale` 留在原地。
注释写着"`locale` is optional"，代码却仍是硬访存。

| 版本 | `exports.inject` | L226 | 真机结果 |
|---|---|---|---|
| 1.8.1 | 含 `locale` | `ctx.locale` | ✅ 在 inject 内，可解析 |
| 1.8.2 | 只剩 `remote` | `ctx.locale`（**漏改**） | 🔴 抛错 → 客户端半边全废 |

**关键教训**：把服务从 inject 里移走时，**必须同时把它所有的直读改成 `ctx.get()`**。
这两件事在 1.8.2 里被拆到了不同地方，且没有任何机制核对它们是否一致 ——
所以 R2 现在是**自动断言**的（见 §8 的 P7），不再依赖人记得。

### 内核集合为什么是"实测"而不是"清单"

`ctx.effect`、`ctx.get`、`ctx.inject` 这类框架内核成员不需要 inject 就能解析，
但**它们的名单会随 cordis 版本变化**，写死在脚本里必然会过期，且过期方式很危险：
名单少一个 → 误报；名单多一个（比如把 `locale` 写进去）→ **漏报，规则失效**。

因此 `scripts/client-probe.mjs` 与 `tests/client-inject-contract.test.ts` 都**实测**：
在一个什么都不提供的真实 `Context` 上挂一个空插件，看哪些名字能解析。同时探测
`locale` / `slots` / `remote` 等**服务名**，断言它们**不在**内核集合里 ——
这一步是反向控制，保证"探测过于宽松导致规则空转"不可能发生。
与 §6 的能力探测同源：**判行为，不判版本号**。

### 规则 R2b：带点的服务名，不能用"父级属性"读

> **R2b**：`<a>.<b>` 是**一个独立的服务名**，不是 `<a>` 服务的属性。
> 只能整体读 `ctx.get('<a>.<b>')`，**禁止** `ctx.get('<a>').<b>`、`ctx.<a>.<b>`、
> `ctx['<a>.<b>']`，也禁止先存进局部变量再点读（`var r = ctx.get('<a>'); r.<b>`）。
> 带点服务名**不得进入 `inject`**。

**机制**（`cordis/lib/index.js` 的 `createTraceable`，L130）：

```js
if (tracker.associate && ctx.reflect.props[`${tracker.associate}.${prop}`])
  return Reflect.get(ctx, `${tracker.associate}.${prop}`, …)
```

服务值本身是个 Proxy，`tracker.associate` 就是它的服务名。**当 `<服务名>.<属性>` 恰好
是一个已注册的服务名时**，读属性会被**改写**成读那个带点服务名 —— 也就是**绕回 inject 门禁**。
注意触发条件不是"父级是 `Service`"，而是"**这个带点名字被注册过**"：

| 读法 | 结果 |
|---|---|
| `ctx.get('remote')` | ✅ 合法（`remote` 在 inject 内） |
| `ctx.get('remote').commands` | 🔴 抛 `cannot get property "remote.commands" without inject` |
| `ctx.remote.commands` | 🔴 同上 |
| `ctx.get('remote.commands')` | ✅ 唯一正解 |
| `ctx.get('slots').inject` | ✅ 普通属性读（`slots.inject` 从未被注册为服务名） |

**为什么必须惰性解析**：带点服务名由"谁先加载谁挂载"决定。1.8.1 是**点击时**才解析，
1.8.3 改成 `apply()` 里解析一次并缓存 —— 即使名字写对了，`apply()` 时命名空间可能还没装上，
按钮就会**永久失效**（且无任何报错）。所以要在**每次调用时**取 `ctx.get('<a>.<b>')` 并判空。

#### 1.8.3 的真机事故（R2b 的由来）

| 版本 | `exports.inject` | L252 | 真机结果 |
|---|---|---|---|
| 1.8.1 | 含 `remote.commands` | `ctx.remote.commands`（点击时读） | ✅ 在 inject 内 |
| 1.8.2 | 只剩 `remote` | 同上（先崩在更早的 locale 行） | 🔴 |
| 1.8.3 | 只剩 `remote` | `ctx.get('remote').commands`（**apply 时读**） | 🔴 同一串报错再次全废 |

**两次事故是同一根因的两种形态**：cordis 里"服务的属性读"可能被改写成服务名读。
R2 管"未注入的直读"，R2b 管"带点服务名的父级属性读"。现在两者都有门禁（见 §8 的 P7）。

#### `NAMESPACE_ROOTS` 为什么只有 `remote`

门禁需要知道"哪些服务的子名会被注册"，这个集合必须是**窄**的：把普通服务的点读也判红，
就会误报 `slots.inject()` / `locale.bind()`，而**会喊狼来的门禁迟早被关掉**。
实测结论（本机 dsh `0.1.5-rc.2`，扫全部 358 个客户端产物文件）：

| 证据 | 结果 |
|---|---|
| 带点服务名 | 共 18 个，**全部以 `remote.` 开头** |
| `super(ctx, '<字面量>')` 的服务名 | 86 个，**无一带点** |
| 唯一用表达式拼带点名的代码 | `dsh-api-gateway` 的 `remoteServiceKey(ns) = 'remote.' + ns`（每个命名空间各自挂一个 `Service`） |

⇒ 只有 `remote` 需要禁止点读；`slots` / `locale` / `sessions` / `settingsScope` 点读安全。

**这个集合不会静默腐烂**：`scripts/client-probe.mjs` 会从**本机已安装的 dsh** 重新推导
命名空间根（识别 `super(ctx, <builder>())` 与 `super(ctx, 'a.b')` 两种注册形态），
与 `NAMESPACE_ROOTS` 不一致就 FAIL，并提示同步更新探针与测试。没有 dsh 安装时
（CI）输出 `[SKIP]` 而**不是** PASS —— 看起来像通过的跳过项正是门禁腐烂的方式。

## 5. 兼容层：`src/compat/`

| 模块 | 职责 | 失败时的行为 |
|---|---|---|
| `freeze.ts` | 自建 `deepFreeze` / `isFrozen`（环形安全、跳过 `AbortSignal`、返回同引用） | 不可能失败 —— 不依赖宿主 |
| `timing.ts` | 自建 `MAX_TIMER_DELAY_MS` / `deadline()` / `timeoutOf()` / `TimeoutReason` | 不可能失败 —— 不依赖宿主 |
| `loader.ts` | 同步 `createRequire` 懒加载宿主包，带缓存，**永不抛错** | 返回 `null` |
| `capability.ts` | 能力探测 + 降级说明 + 启动报告 | 缺失能力记为 `null`，由调用方降级 |
| `scope.ts` | `ctx.inject` 的防御式包装（框架无此 API 时立即执行） | 注册失败仅 WARN |

`TimeoutReason` 采用**结构化判别**（检查 `name === 'TimeoutReason'` + `code` + `timeoutMs`），
而非 `instanceof` —— 因为宿主的类可能存在多份副本，`instanceof` 会误判。

## 6. 能力探测与降级行为表

**不判版本号**：版本号变了不代表能力变了，而且 patch 版本也会搬走导出（1.8.1 正是如此）。
只判**函数是否存在且类型正确**。

| 能力 | 来源 | 不可用时的行为 |
|---|---|---|
| `deepFreeze` | 自建 | 不可能不可用 |
| `deadline` / `timeoutOf` / `MAX_TIMER_DELAY_MS` | 自建 | 不可能不可用 |
| `z`（schemastery） | `dependencies` | 构建期即失败 → `preflight` 前置拦截 |
| `Service`（cordis） | 静态 import | **残余风险**，见 §9 |
| `defineTool` | `dsh-tools` | 不注册 `prompt_optimize` 工具 + WARN；`/optimize` 命令与输入框按钮**不受影响** |
| `createUserMessage` | `dsh-llm` | 关闭 autoOptimize 前缀替换 + WARN；其余功能不受影响 |
| `BlockAssembler` | `dsh-llm` | `/optimize` 返回错误码 `UNSUPPORTED_ENV` + 明确文案（**不伪造消息、不静默失败**） |
| `llm` / `tools` / `systemPrompt` / `commands` 服务 | `ctx` | 按功能门禁：任一项缺失只关掉对应功能 |

**降级可见性**：降级本质是"静默减功能"，因此**插件构造时必定打印一行 compat report**：

```
prompt-optimizer: host compat ok (defineTool=ok createUserMessage=ok BlockAssembler=ok)
prompt-optimizer: host compat DEGRADED (defineTool=MISSING …) — defineTool: the `prompt_optimize` tool is not registered; the /optimize command and the input-box button still work | …
```

健康时是 `info`，降级时是 `warn` —— 事故可发现，而不是靠人猜。

## 7. 兼容矩阵

| 宿主变化类型 | 1.8.1 及以前 | 1.8.2 起 |
|---|---|---|
| 某工具函数被移出包 / 改名（`deepFreeze` 事故） | 🔴 **宿主启动失败** | ✅ 该功能降级 + 一行 WARN，宿主与其余功能正常 |
| 域包整体升级（`0.1.5-rc` → `0.2.x`） | ⚠️ 未知，可能直接崩 | ✅ 能力探测决定可用面；不可用即降级 |
| 某服务改名（如 `systemPrompt`） | 🔴 插件不加载 | ✅ 仅该系统提示词引导消失 |
| 客户端**可选服务**缺失 / 改名（`locale` / `sessions` / `settingsScope`） | 🔴 直读即抛错，客户端半边完全不注册（1.8.2 的真机事故） | ✅ 走 `ctx.get()`：只少对应文案或入口，✨ 按钮与设置页照常注册（R2 + P7 守着） |
| 客户端读了**带点服务名**的父级属性（如 `ctx.get('remote').commands`） | 🔴 被改写回 inject 门禁并抛错，客户端半边完全不注册（1.8.3 的真机事故） | ✅ 整体 `ctx.get('<a>.<b>')` 且按调用时解析：命名空间缺失只让按钮报"通道不可用"（R2b + P7 守着） |
| 客户端 slot props 契约改名 | 🔴 按钮恒 disabled（或消失） | ✅ 候选链自适配；全部失败则不注册 + 自诊断日志 |
| `dsh.client.inject` 中某包被移除 | 🔴 客户端 bundle 不注册 | ✅ `preflight` P2 提前拦截；运行时仅少一项 |
| 宿主 prerelease 版本继续前进 | ⚠️ peer 范围静默不满足 | ✅ 不再有 dsh 域包 peer 声明，无告警 |

### 为什么不用 peer 范围来保证兼容

用宿主自带的 node-semver 实测（`satisfies(version, range)`）：

| version | range | 结果 |
|---|---|---|
| `0.1.5-rc.2` | `^0.1.0-rc.6` | **false** |
| `0.1.5-rc.2` | `>=0.1.0-rc.6 <0.2.0` | **false** |
| `0.1.5-rc.2` | `*` | **false** |
| `0.1.5-rc.2` | `^0.1.5-rc.1` | true |

**根因**：semver 的 prerelease 排除规则 —— 待测版本是 prerelease 时，range 中必须存在
**同 `[major,minor,patch]` 的 prerelease 比较器**才可能匹配，否则一律 `false`（连 `*` 都不例外）。

⇒ 唯一能匹配当前宿主的写法是 `^0.1.5-rc.1`，而它在宿主升到 `0.1.6-rc.x` 时立刻失效。
**peer 范围无法表达"兼容未来 prerelease"**，因此本插件对 dsh 域包不作 peer 声明，
兼容性改由**运行时能力探测**（§6）+ **发布前门禁**（§8）保证。唯一保留的硬 peer 是
`@deepseek-ai/cordis`。

## 8. 验证方式：命令与探针

### `node scripts/preflight.mjs`

发布前必跑的七道门禁：

| 步骤 | 检查内容 | 失败即 FAIL |
|---|---|---|
| **P1** | **依赖面审计**：扫 `lib/**/*.js` 顶层裸包 import，白名单 = cordis + 自有 `dependencies` | 新增了任何其它裸包静态 import（含 `import {}` 空绑定形式） |
| **P2** | **inject 存在性**：从宿主**实际加载插件的目录**解析 `dsh.client.inject` 每一项 —— 即走 Node 真实的查找顺序（profile 层 → 共享 anchor 层 → CLI 内嵌），并报告解析来源层级 | 出现死 id（1.8.1 客户端不注册的根因）。插件未装时退化为目录列举并标注 `approximate`；无 profile 时 SKIP |
| **P3** | **产物一致性**：`client/client.js` 与 `lib/client.js` 字节相同 | 忘了跑 `copy-client.mjs` |
| **P4** | `typecheck` → `test` → `build` | 任一失败 |
| **P5** | **兼容性报告**：打印宿主版本 + 能力探测结果 | 仅提示，不阻断 |
| **P6** | **启动独立性**：见下 | 入口无法在宿主缺席时实例化 |
| **P7** | **客户端服务读取契约（规则 R2 / R2b）**：见下；另从本机 dsh 重新推导命名空间根做交叉校验 | 出现未注入服务的直读（1.8.2 根因）、带点服务名的父级属性读（1.8.3 根因）、`apply()` 在忠实最小宿主面上没注册出两个 slot，或推导出的命名空间根与守卫集合不一致 |

选项：`--offline`（跳过 P4）、`--skip-tests`（P4 不跑测试，CI 用）。

> P4 调用 pnpm 时带 `--config.verify-deps-before-run=false`：裸 `pnpm run` 会先重新校验
> 依赖图，在 link farm 看起来陈旧时**静默重装** —— 只读门禁不该改动 `node_modules`。

### `node scripts/startup-probe.mjs` —— I1 的动态证明

在一个子进程里**同时封死两条模块解析路径**上的所有 `@deepseek-ai/dsh*`：

- **ESM `resolve` hook** —— 静态 `import` 走的路径，其失败不可捕获（1.8.1 的炸点）；
- **`Module._load` CJS 拦截** —— `compat/loader.ts` 特意改走的路径，必须**软失败**。

然后导入 `lib/index.js` 并断言：入口仍能实例化、能力探测全部读作缺失、降级被报告出来。

探针内含**反向控制**（先断言封印真的生效），避免"封印没生效 → 断言空转 → 永远 PASS"这种假绿。

```
[PASS] control — the ESM seal rejects @deepseek-ai/dsh-llm
[PASS] control — the CJS seal rejects require("@deepseek-ai/dsh-llm")
[PASS] lib/index.js instantiated with every host package sealed
[PASS] capability probe degraded cleanly (defineTool=MISSING createUserMessage=MISSING BlockAssembler=MISSING)
[PASS] degradation is reported: prompt-optimizer: host compat DEGRADED (…)
```

P1 是**静态证明**（产物里不存在运行时宿主导入），P6 是**动态证明**（宿主真没了也能起来）。
两者互补：P1 覆盖 ESM 路径的代码面，P6 覆盖两条路径的实际行为。

### `node scripts/client-probe.mjs` —— R2 / R2b 的证明（静态 + 动态 + 推导）

锁都作用在产物 `lib/client.js` 上：

1. **静态**：扫服务读取，凡既不在 `exports.inject` 内、也不是 cordis 内核成员、也不是
   "整体点名"的带点服务名，即为违规（报告行号与修法）。覆盖四种写法：
   `ctx.<name>`、`ctx['<name>']`、`ctx.get('<name>').<child>`、以及别名形态
   （`var s = ctx.get('<name>')` … `s.<child>`）。
   内核集合由**实测**得出（§4）；命名空间根集合由**推导**交叉校验（§4 的 R2b）。
2. **动态**：用真实 cordis `Context` 建一个**忠实的最小宿主** —— `remote` 与
   `remote.commands` 都用 `new Service(ctx, name)` 注册（与 `dsh-api-gateway` 一致），
   `slots` / `locale` 为普通 provide —— 加载手写的 ModuleLoader bundle 并**真正调用 `apply()`**，
   断言两个 slot 都注册；再提供 `locale` 跑一遍断言语言字典被注册；再断言
   `ctx.get('remote.commands').execute()` 能**真的往返**（否则"不抛错"可能只是因为什么都取不到）。
3. **推导**：从**本机已安装的 dsh** 重新推导命名空间根，与 `NAMESPACE_ROOTS` 不一致即 FAIL。
   无 dsh 安装时输出 `[SKIP]`（CI），**不是** PASS。

**七个反向控制**保证它不可能"永远 PASS"：内核探测必须能区分内核与服务名、静态扫描必须能咬住
合成的 `ctx.locale`（1.8.2）与合成的带点读（1.8.3）、必须**放行**合法的 `slots.inject()` /
`ctx.get('remote.commands')`（防误报）、宿主模型必须**有对抗性**（`ctx.get('remote').commands`
在该宿主上必须抛）、动态 harness 必须能在 apply 路径上复现两次事故的抛错。

```
[PASS] control — kernel probe discriminates core members (effect, events, fiber, get, inject, logger, plugin, provide, reflect, set)
[PASS] control — the static scan flags a synthetic `ctx.locale` read (1.8.2)
[PASS] control — the static scan flags a nested-service read (1.8.3)
[PASS] control — the static scan leaves `slots.inject()` / `ctx.get('remote.commands')` alone
[PASS] control — the host model is adversarial ("cannot get property "remote.commands" without inject")
[PASS] control — the dynamic harness reproduces the 1.8.2 `without inject` failure
[PASS] control — the dynamic harness reproduces the 1.8.3 failure ("cannot get property "remote.commands" without inject")
[PASS] derivation — installed dsh namespace roots match [remote]
[PASS] declared inject parsed: [remote]
[PASS] inject holds only services the client half cannot work without
[PASS] no read of a service that is neither injected, a core member, nor reached as a nested name
[PASS] apply() registers both slots on a host with only slots + remote provided
[PASS] apply() survives a host where the remote.commands namespace is not mounted yet
[PASS] locale dictionaries registered as prompt-optimizer-client (zh + en)
[PASS] ctx.get('remote.commands').execute() round-trips on the faithful host
```

> ⚠️ **动态那半的宿主必须"忠实"，否则等于没有**。1.8.3 之所以能穿过当时的全部门禁，
> 就是因为假宿主用普通对象 `{ commands: … }` 提供 `remote` —— 那样 `.commands` 只是普通属性读，
> **永远不会抛**。所以门禁里专门有一条控制断言"naive 写法在这个宿主上必须抛"；
> 宿主模型一旦退化，控制会先红，而不是断言静默空转。

源码层有同一规则的两个测试（`pnpm test` 覆盖，P7 则在 `--skip-tests` 时兜底）：
`tests/client-inject-contract.test.ts`（静态，13 例）与 `tests/client-apply.test.ts`（动态，10 例）。

> **P7 的边界（诚实标注）**：只覆盖客户端半边。宿主半边把服务读取放在
> `compat/scope.ts` 的 `scopedInject()` 回调里，逐行扫描无法判断作用域，会把合法的 scoped 读
> 全部误报 —— 宿主侧仍然由 P1（依赖面）与 P6（启动独立性）覆盖。

### 升级 dsh 后的验证步骤

```bash
pnpm install                 # 或 pnpm update（跟随最新 rc）
pnpm typecheck && pnpm test  # 类型与行为
pnpm preflight               # P1–P7 全 PASS 才算安全（P2 需要本机有 dsh profile）

```

改动客户端半边时，P7 的**动态**那一半尤其值得盯：它是本项目里唯一会真正执行
`client/client.js` 的自动化步骤。1.8.2 之所以把事故送到真机，正是因为当时不存在这一步。

按 R2 / R2b 查那段 `apply()` 里的服务读取（`client-probe` 与两个测试都应当已提前捕获）：

| 控制台里的名字 | 违反的规则 | 正解 |
|---|---|---|
| `cannot get property "locale" without inject` | R2（未注入服务的直读） | 改 `ctx.get('locale')` |
| `cannot get property "remote.commands" without inject` | R2b（带点服务名的父级属性读） | 改 `ctx.get('remote.commands')`，并**按调用时**解析 |

## 9. 残余风险（诚实标注）

1. **`@deepseek-ai/cordis` 仍为静态 import**。技术上无法消除：它是宿主框架本体
   （`Service` 基类、`Context` 类型）。若 cordis 未来大版本重构，本插件需同步改写 ——
   这是"插件与框架共生"的固有成本。风险等级远低于域包：域包随 rc 频繁改名/搬迁，
   而 cordis 4.x 未动过 `Service`。
2. **`schemastery` 仍为静态 import**，但写在 `dependencies`（自己安装），解析自我保证，不依赖宿主。
3. **同步 `require(ESM)` 依赖 Node ≥ 22.12**。更老运行时下 `require` 抛错被捕获 →
   相关功能降级（**不崩**）。当前实测环境 Node v22.22.2 正常。
4. **降级是"静默减功能"**，因此必须保证 WARN 可被发现 —— 补偿机制是"构造时必定打印一行 compat report"。
5. **`preflight` P2 需要真实的 dsh profile 环境**；纯离线 CI 只能跑 P1/P3/P4/P6，P2 在本地发版前执行。
   可用 `--dsh-home <path>` 指定目标 profile。
   ⚠️ P2 必须**模拟真实解析**才可信：列举 `node_modules` 目录会与 Node 的查找顺序背离 ——
   profile 层的 `@deepseek-ai/*` 常是指向 dsh CLI 内嵌的 junction，`require.resolve` 会按 realpath
   落到 CLI 自带的 `node_modules`，那是列举法**从来不看的目录**。于是旧版列举法能在
   宿主实际解析到别处时仍报 PASS。现在的实现从插件安装目录发起解析，与宿主同一条查找路径。
6. **客户端 composer 契约靠候选链猜测**。dsh 客户端 slot props 的契约未被文档化，`resolveDraft`
   按 `useInput` hook → `props.input.draft` → `props.hooks.input.draft` 依次尝试。
   若未来契约变成第四种形状，按钮会**不注册并打印自诊断日志**（而非静默失效）——
   这时需要照着日志补一条候选分支。
7. **P7 只覆盖"注册"这一段，不覆盖"渲染"那一段**。`client-probe` 与两个测试执行的是
   `apply()`（服务读取 + slot 注册），这正好是 1.8.2 的炸点所在；但组件真正渲染成按钮时
   才会走到的路径（`props` 契约、样式注入、`aria`），仍然**只有真机能验证** ——
   本包没有 `react-dom`（peer 是 `react`），服务端渲染那一步做不了。
   所以"按钮出现且可点"这一条，最终仍以真机为准；自动化能保证的是它不会被
   `apply()` 阶段的异常整体吞掉。
8. **`--skip-tests` 与 `pnpm test` 覆盖的是不同层**。P7 检查**产物** `lib/client.js`，
   两个测试检查**源码** `client/client.js`。两者由 P3（字节一致）绑定，所以任一单跑都可信；
   但如果有人绕过 P3（例如手工改 `lib/`），P7 也可能一并被骗过。正常发布流程不会出现这种状态。
9. **`NAMESPACE_ROOTS` 是显式集合，靠推导步骤防腐烂**。规则 R2b 需要知道"哪些服务的子名会被
   注册"，而这只能从宿主代码里读出来，所以集合是写死的（当前 `['remote']`）。
   防腐烂手段是 P7 的推导步骤：从本机 dsh 重新推导，不一致即 FAIL。
   ⚠️ 该步骤在**没有 dsh 安装的环境（CI）下是 `[SKIP]`**，所以"上游新增带点服务名"这件事
   只在**本地发版前**会被拦下 —— 这与 P2 的边界相同（都依赖本机有 dsh）。
10. **静态扫描是行级正则，不是 AST**。它能覆盖 `ctx.<a>.<b>` / `ctx['<a>.<b>']` /
    `ctx.get('<a>').<b>` / 别名点读四种已知形态，但**构造性规避**（动态拼名字、`eval`、
    把服务值传进别处再取属性）扫不出来。这类写法在本项目里从未出现，且动态那一半
    （在忠实宿主上真跑 `apply()`）对其中相当一部分仍能兜住。
